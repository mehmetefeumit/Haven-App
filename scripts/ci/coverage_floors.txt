# Per-path coverage floors — the minimum each security- or privacy-critical
# path may fall to, and the level past which it must be re-pinned.
#
# Enforced by scripts/ci/check_coverage_floors.sh (see that file's header for
# the mechanism, the ratchet, and why a stale entry is a hard failure).
#
# Format, one entry per line:
#
#     <stack>|<path>|<floor-percent>[|<ratchet-margin>]
#
#   stack     rust (haven-core) | flutter (haven) — reconciled independently,
#             so a rust row is never reported stale while checking flutter.
#   path      Relative to the STACK ROOT. A trailing `/` means "directory" and
#             AGGREGATES every file beneath it; anything else is a glob over the
#             file path. Directory and file rows deliberately overlap: the
#             directory catches slow layer-wide drift, the file row catches one
#             critical file being hollowed out while its neighbours compensate.
#   floor     Whole percent. Line coverage — the same metric the 80%/50%
#             aggregate gates use, read from the same lcov report.
#   margin    Optional. Points above the floor at which the run fails asking for
#             a re-pin. Defaults to 5; raise it only for a path so small that
#             one line is worth several points.
#
# Regenerate every row against a fresh report with:
#   scripts/ci/check_coverage_floors.sh --list rust    haven-core/coverage.lcov
#   scripts/ci/check_coverage_floors.sh --list flutter haven/coverage/lcov.info
#
# ===========================================================================
# LOWERING A FLOOR IS NOT A FIX.
#
# These numbers exist because the 80%/50% gates are AGGREGATES, and an
# aggregate is a budget the whole crate shares. When this file was pinned,
# haven-core had ~2290 lines of slack over its 80% gate and haven had ~1588
# over its 50% — enough for any single file here to fall to zero with the gate
# still green. A row that goes red is telling you a specific proof stopped
# running; editing the number down converts a measured regression into a
# permitted one and leaves nothing behind to notice it again.
#
# The legitimate reasons to EDIT a number are: the ratchet asked you to raise
# it (do so, using the value in the failure message), or the path genuinely
# moved (update the pattern — do not delete the row, an entry matching nothing
# fails on purpose).
# ===========================================================================
#
# All values below were measured on 2026-08-03 from
#   cargo llvm-cov --all-features --lcov --ignore-filename-regex 'frb_generated'
#   flutter test --coverage
# and pinned at floor(measured) - 2, or exactly 100 where the path is fully
# covered (see the guard header: the margin rule cannot ratchet a 100% path).
#
# ===========================================================================
# MEASURE WITH THE TOOLCHAIN CI USES, OR THE NUMBERS ARE NOT COMPARABLE.
#
# The denominator here is INSTRUMENTED LINES, and how many lines LLVM
# instruments is a property of the LLVM version, not of the tests. The rust
# rows were first pinned against rustc 1.92 and CI runs `dtolnay/rust-
# toolchain@stable` — 1.97.1 at the time of writing, LLVM 22.1.6 — which
# instruments 1-4% FEWER lines per path. Same tests, same hits, smaller
# denominator, so every percentage read higher in CI than in the pin: seven
# paths tripped the ratchet on the first run (30833142781) with nothing about
# the code having changed. They are re-pinned below against 1.97.1.
#
# The dangerous direction is the other one. Re-running `--list` on an OLDER
# toolchain reads every path 1-4 points LOW and emits a row for each — which,
# pasted in, silently LOWERS all thirty floors while looking like routine
# maintenance. So: re-pin from a CI report, or from a local run on the
# toolchain CI resolves (`rustup toolchain install <ver>` and
# `cargo +<ver> llvm-cov …`). If the numbers you measure sit uniformly below
# the comments below, that is the toolchain, not a regression.
#
# Hit counts also wobble a few lines run to run on the concurrency-sensitive
# paths (src/relay/live_sync/ moved 4 lines between two runs of the same
# commit). That is what the two points of headroom absorb, and it is why the
# pin is floor(measured) - 2 rather than the tighter value the ratchet's
# failure message suggests — `--list` implements the former, and it is the
# supported way to re-pin.
#
# THE PRE-PUSH HOOK RUNS THIS FILE TOO, and it runs on whatever `cargo` is
# default. On a toolchain older than CI's, some rows are not merely tighter —
# they are UNSATISFIABLE. Measured on rustc 1.92 against these 1.97.1 pins:
#
#   src/profile/fetch.rs   floor 97, ceiling 96.26%  (2 uncovered production
#                          lines; 410+2 = 412/428)
#   src/keyring_policy.rs  floor 89, ceiling 88.00%  (4 uncovered production
#                          lines; 172+4 = 176/200)
#
# "Ceiling" is with EVERY remaining production line covered. The rest of each
# file's uncovered lines are assertion-failure messages inside passing tests,
# which execute only when the assertion fails — no test can cover them. So on
# 1.92 those two rows cannot be satisfied by writing tests, only by matching
# CI's toolchain (`rustup update`, or run the hook with `cargo +<ci-ver>`).
# ===========================================================================

# --- Relay plane -----------------------------------------------------------
# publishers.rs carries the OK-ack accounting Security Rule 13 depends on
# ("acked" must never mean "sent").
#
# catchup.rs is the background-wake receive path: fetch since the cursor,
# ingest, persist, re-broadcast auto-commits, advance the cursor. Until
# tests/catchup_sweep_e2e.rs only its cursor ARITHMETIC was exercised — the
# sweep itself ran nowhere, which is how a path that decides what a
# backgrounded device keeps and what it silently skips sat at 28.92%. The
# remaining ~5% is deliberate: the saturation counter needs a 512-event
# window, the `Buffered` arm needs an out-of-order epoch, and the rest are
# defensive arms (storage down, whole-batch fetch error, a circle stored with
# no relays) that the public API cannot reach — forcing them would mean
# fabricating states production cannot produce. The open `limit(512)` paging
# defect (P0-4) is NOT covered by these tests and must not be read as settled.
#
# auto_commit.rs is pinned at 100, not because a round number is tidy but
# because it is the whole of Rule 13's RECEIVE side: every branch there ends in
# either `confirm_published` or `publish_failed`, and the ones that were
# uncovered were exactly the fail-closed ones (no relay plane wired, an
# unconvertible commit, send-side work on a receive batch). A regression turning
# any of them into an optimistic confirm applies a commit no relay ever saw and
# forks the group — silently. At 100 the floor trips on the first uncovered
# line; anything lower licenses one of those branches to stop being exercised.
# Pinned exactly (the margin rule cannot ratchet a 100% path — see the guard
# header). Proofs: tests/selfremove_autopublish_e2e.rs.
