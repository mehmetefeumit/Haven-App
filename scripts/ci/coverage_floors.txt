# Per-path coverage floors — the minimum each security- or privacy-critical
# path may fall to, and the level past which it must be re-pinned.
#
# Enforced by scripts/ci/check_coverage_floors.sh (see that file's header for
# the mechanism, the ratchet, and why a stale entry is a hard failure).
#
# Format, one entry per line:
#
#     <stack>|<path>|<floor-percent>[|<ratchet-margin>]
#
#   stack     rust (haven-core) | flutter (haven) — reconciled independently,
#             so a rust row is never reported stale while checking flutter.
#   path      Relative to the STACK ROOT. A trailing `/` means "directory" and
#             AGGREGATES every file beneath it; anything else is a glob over the
#             file path. Directory and file rows deliberately overlap: the
#             directory catches slow layer-wide drift, the file row catches one
#             critical file being hollowed out while its neighbours compensate.
#   floor     Whole percent. Line coverage — the same metric the 80%/50%
#             aggregate gates use, read from the same lcov report.
#   margin    Optional. Points above the floor at which the run fails asking for
#             a re-pin. Defaults to 5; raise it only for a path so small that
#             one line is worth several points.
#
# ===========================================================================
# DO NOT EDIT A FLOOR BY HAND. TWO COMMANDS MAINTAIN THIS FILE.
#
#   scripts/ci/check_coverage_floors.sh --lint [--fix]
#       Static, no coverage run, ~50 ms. Every floor must equal the pin rule
#       applied to its own `# measured N%` provenance. Runs in repo-guards.yml,
#       in the pre-commit hook, and as the first step of the local gate.
#
#   scripts/ci/check_coverage_floors.sh --repin <stack> <lcov>
#       Raises floors the code has outgrown and refreshes their provenance,
#       in place, preserving every comment and column. It NEVER lowers one: a
#       row whose coverage fell is left byte-for-byte alone.
#
# Hand-editing is what broke this file. Three rows had been tightened past the
# rule over time — `lib/src/services/` at 51 against a measured 51.06%,
# `src/relay/catchup.rs` at 97 against 97.14%, `geolocator_location_service.dart`
# at 86 against 86.72% — leaving 0.06, 0.14 and 0.72 points of headroom on rows
# the rule pins at 49, 95 and 84. Those are tripwires, not floors. The first
# reddened CI (run 30964250098) when unrelated work moved the services
# aggregate by seven hundredths of a point; the other two were one line of new
# code from the same. `--lint` now fails on that shape in under a second.
#
# THE PIN RULE: floor = floor(measured) - 2, clamped at 0, or exactly 100 for a
# fully covered path (the margin rule cannot ratchet a 100% path — there is no
# 103% to reach). Two points of headroom below absorbs run-to-run wobble and a
# few new lines landing in a pinned path; the ratchet margin above (default 5)
# asks for a re-pin once the code has genuinely outgrown the number.
# ===========================================================================
#
# ===========================================================================
# LOWERING A FLOOR IS NOT A FIX.
#
# These numbers exist because the 80%/50% gates are AGGREGATES, and an
# aggregate is a budget the whole crate shares. When this file was pinned,
# haven-core had ~2290 lines of slack over its 80% gate and haven had ~1588
# over its 50% — enough for any single file here to fall to zero with the gate
# still green. A row that goes red is telling you a specific proof stopped
# running; editing the number down converts a measured regression into a
# permitted one and leaves nothing behind to notice it again.
#
# This is why `--repin` is one-directional, and why a row it reports as HOLD
# (measured now below the pin rule) needs TESTS, not a smaller number. The two
# legitimate reasons a floor changes are: the tooling raised it, or the path
# genuinely moved (update the pattern — do not delete the row, an entry
# matching nothing fails on purpose).
# ===========================================================================
#
# All values below were measured from CI run 30964250098 (2026-08-04) on the
# toolchains pinned in scripts/ci/coverage_toolchain.env, via
#   cargo llvm-cov --all-features --lcov --ignore-filename-regex 'frb_generated'
#   flutter test --coverage
#
# ===========================================================================
# MEASURE WITH THE TOOLCHAIN CI USES, OR THE NUMBERS ARE NOT COMPARABLE.
#
# The denominator here is INSTRUMENTED LINES, and how many lines get
# instrumented is a property of the compiler, not of the tests. The rust rows
# were first pinned against rustc 1.92 while CI floated on
# `dtolnay/rust-toolchain@stable`, which had moved to 1.97.1: 400 fewer
# instrumented lines in haven-core, same tests, same hits, every path reading
# 1-4 points higher, and seven rows tripping the ratchet in one run
# (30833142781) with nothing about the code having changed.
#
# The dangerous direction is the other one. Re-measuring on an OLDER toolchain
# reads every path 1-4 points LOW, and a re-pin taken from that would silently
# lower thirty floors while looking like routine maintenance. `--repin` cannot
# do it (it never lowers), but a hand edit could.
#
# So the coverage jobs no longer float: scripts/ci/coverage_toolchain.env pins
# the rustc and Flutter versions that both .github/workflows/coverage.yml and
# scripts/ci/check_coverage.sh measure with, and the local gate refuses to run
# on a different rustc rather than compare against floors it may be unable to
# satisfy. On rustc 1.92, for instance, `src/profile/fetch.rs` tops out at
# 96.26% under a floor of 97 and `src/keyring_policy.rs` at 88.00% under 89 —
# with EVERY remaining production line covered, because the rest are
# assertion-failure messages that only execute when a test fails. Bumping the
# pin and re-pinning the floors belong in ONE commit; see that file's header.
#
# Hit counts still wobble a few lines run to run on the concurrency-sensitive
# paths (src/relay/live_sync/ moved 4 lines between two runs of the same
# commit). That is what the two points of headroom absorb.
# ===========================================================================

# --- Relay plane -----------------------------------------------------------
# publishers.rs carries the OK-ack accounting Security Rule 13 depends on
# ("acked" must never mean "sent").
#
# catchup.rs is the background-wake receive path: fetch since the cursor,
# ingest, persist, re-broadcast auto-commits, advance the cursor. Until
# tests/catchup_sweep_e2e.rs only its cursor ARITHMETIC was exercised — the
# sweep itself ran nowhere, which is how a path that decides what a
# backgrounded device keeps and what it silently skips sat at 28.92%. The
# remaining ~5% is deliberate: the saturation counter needs a 512-event
# window, the `Buffered` arm needs an out-of-order epoch, and the rest are
# defensive arms (storage down, whole-batch fetch error, a circle stored with
# no relays) that the public API cannot reach — forcing them would mean
# fabricating states production cannot produce. The open `limit(512)` paging
# defect (P0-4) is NOT covered by these tests and must not be read as settled.
#
# auto_commit.rs is pinned at 100, not because a round number is tidy but
# because it is the whole of Rule 13's RECEIVE side: every branch there ends in
# either `confirm_published` or `publish_failed`, and the ones that were
# uncovered were exactly the fail-closed ones (no relay plane wired, an
# unconvertible commit, send-side work on a receive batch). A regression turning
# any of them into an optimistic confirm applies a commit no relay ever saw and
# forks the group — silently. At 100 the floor trips on the first uncovered
# line; anything lower licenses one of those branches to stop being exercised.
# Pinned exactly (the margin rule cannot ratchet a 100% path — see the guard
# header). Proofs: tests/selfremove_autopublish_e2e.rs.
